# 校正モード

agy に文章の校正案を出させ、Claude が案を一件ずつ判定してから、原文のコピーに適用する。
2026-10-14 に v1.3.4 で、オンボーディング資料の HTML（約 36KB）を使って一連の手順を確認した。

## agy に直接書き換えさせない理由

- ヘッドレスで「ファイルを直接編集して」と頼むと、agy は置換用の Python スクリプトを書いて実行しようとする。シェルコマンドは拒否されるので、何も変わらないまま `SUCCESS` で戻り、`response` も空になる（検証済み）
- 案の中に、事実や確度を変えてしまう書き換えが一定の割合で混じる（下の「判定の観点」を参照）。直接書き換えさせると、それを止める機会がなくなる

そこで `--json-schema` を使い、修正案だけを構造化して返させる。agy はファイルを読むだけで済み、権限の許可ルールも要らない。

## 手順

1. **原文を退避する。** 原文はそのまま置き、scratchpad に作業用のディレクトリを作ってコピーする。agy はこのコピーのあるディレクトリで実行する。
2. **文章規範のスキルを確認する。** agy のグローバルスキルは `~/.gemini/config/skills/<name>/SKILL.md` に置く（各スキルはディレクトリの直下に置く）。日本語の技術文書・社内資料には `japanese-tech-writing` を使う。ユーザーが別の規範を指定したら、その中身を読んでから同じ場所に入れる。読んでいないスキルは入れない。
3. **agy を実行する。**

   ```bash
   S=~/.claude/skills/antigravity-cli/scripts
   (cd "<作業ディレクトリ>" && agy -p "<下の依頼文>" --json-schema "$S/proofread-schema.json" --output-format json --print-timeout 20m < /dev/null > "<scratchpad>/agy-out.json" 2> "<scratchpad>/agy-err.txt"); echo "exit=$?"
   ```

   - `--mode` は付けない。編集させないので不要
   - 36KB の HTML で数分かかった。Bash は `run_in_background` で回し、完了の通知を待つ
   - 結果は `structured_output.edits` に入る。`response` は agy が書いた説明文なので、読み飛ばしてよい

4. **案を一件ずつ判定する。** 下の観点で全件を読み、`decisions.json` に不採用（reject）と修正採用（override）を書く。採用する案は書かなくてよい。
5. **適用する。**

   ```bash
   python3 -I "$S/apply_edits.py" "<原文のコピー>" "<scratchpad>/agy-out.json" "<scratchpad>/decisions.json" "<出力先>"
   ```

   - 一致しない `old`、複数箇所に一致する `old`、タグを含む `old`/`new`、HTML のタグ構造やテキストノード数の変化があれば、ファイルを書かず exit 1 で終わる。その案を reject に入れるか override で直して再実行する
   - 標準出力に、案ごとの「採用／修正採用／不採用、修正前、修正後、理由」がタブ区切りで出る。報告にはこれを使う

6. **出力先** は原文と同じディレクトリの `<元の名前>-校正済.<拡張子>`。原文は上書きしない。スクリプトは既にあるファイルにも書き込まない。

## 依頼文の雛形

```
<スキル名> スキルを読み込み、その規範に従って <ファイル名> の日本語の文面を校正する修正案を出してください。

- ファイルは編集しないこと。コマンドも実行しないこと。修正案は出力のJSONだけで返す。
- old は原文と1文字も違わない部分文字列で、ファイル内で1箇所だけに一致すること。
- old と new には < や > を含めないこと。1つの要素のテキストの中だけを書き換え、要素をまたいで文を統合・分割しないこと。
- 事実・数値・固有名詞・日付・URL・社内の呼称（略語や機能名）を変えない。
- 確度を変えない。「方向」「話が出ている」「〜の予定」「私案」などを、「方針」「決定」「合意」「計画が進んでいる」へ強めない。推量・未確定の表現は残す。
- 文を追加・削除して情報量を変えない。言い回しの修正にとどめる。
- reason には、どの規範に基づく修正かを1行で書く。
```

## 判定の観点

1 回目の実行（44 件）で実際に出た問題。これに当たる案は reject か override にする。

| 種類 | 実例（修正前 → agy の案） | 判定 |
| --- | --- | --- |
| 確度を強める | 「方向が共有された」→「方針が共有された」、「話が出ています」→「計画が進んでいます」、「会議での方針」→「会議での合意方針」 | 元の語に戻す |
| 決めた主体を変える | 「GOが出ています」→「方針が合意されました」 | 不採用 |
| 指示の向きを変える | 「下の6分類」→「上記の6分類」 | 不採用 |
| 主張の対象を変える | 「本資料はDSSのロール数を断定しません」→「DSSのロール数は未確定」 | 不採用 |
| 社内の呼称を変える | 「Biz／Eng」→「Business・Engineer」、「おすすめ学習」→「推奨学習」、「元の会話」→「一次情報」 | 呼称だけ元に戻す |
| 具体を抽象に置き換える | 「9/24の選択式＋記述式」→「9/24の出題形式の決定」 | 具体を残す |
| 内容を足す | 何が難しいかの説明を agy が創作して補う（試験用の小さなファイルで発生） | 不採用 |

判定に迷う案は採用しない。報告で「保留」として挙げ、ユーザーに見てもらう。

## 報告

- 出力先のパス、採用／修正採用／不採用の件数、HTML 構造の照合結果を最初に書く
- 不採用と修正採用は、理由を種類ごとにまとめて示す
- agy の案を Claude が直したことを隠さない。「agy が校正した」とだけ書かない
